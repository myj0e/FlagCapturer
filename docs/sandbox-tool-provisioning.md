# 沙箱缺少工具的问题与按需供应方案

本文记录沙箱工具供应的机制建议，供后续开发讨论使用，尚不代表已实现。

## 问题

Agent 在 Docker 沙箱中解题时，经常遇到缺少命令、Python 库或专用工具链的情况，例如缺少 tesseract、OpenCV（cv2）和 pytesseract，导致图像分析无法继续。

目前两种直接处理方式都有明显不足：

- 允许 agent 自行联网安装：题目内容和工具输出可能影响安装行为；解题容器获得网络后，也可能访问无关服务、下载不可信内容或外传题目数据。
- 禁止安装，事后人工升级镜像：解题被阻塞，用户需要反复检查依赖、修改构建配置、构建镜像并重新运行，响应慢、操作繁琐。

目标是在保持解题环境无网络、非 root 和受控挂载的前提下，让大多数缺工具问题能够在解题过程中自动解决，并保留版本、来源和执行证据。

## 核心方案

**允许 agent 申请工具，由控制器在独立环境中准备，再交给无网络的解题沙箱使用。**

工具供应服务属于控制器能力。Agent 不直接获得软件安装网络，不提交任意宿主安装命令，也不接触 Docker socket。软件源、依赖解析、资源限制和工具交付由程序执行，不能仅依靠提示词约束。

这将工具安装所需的网络与解题过程分离：只有临时构建容器能够访问规定的软件仓库；实际执行题目、脚本和附件的容器仍保持无网络。

## 工作流程

1. **发现缺失能力**：agent 通过 `tool_request` 描述所需能力或软件包，例如“OCR，需要 tesseract、cv2、pytesseract”。控制器检查已有工具、缓存及可替代能力，避免重复安装。
2. **解析请求**：控制器将请求转换为明确的软件源、包名、版本、架构和依赖集合。自然语言描述不直接转换为任意 shell 命令执行；构建步骤使用受控模板。
3. **独立准备**：缓存未命中时启动临时构建容器。它不接触题目附件、解题工作区、模型凭据或宿主 Docker socket，仅能访问允许的软件仓库。依赖安装和构建脚本在这个隔离环境中执行。
4. **生成工具产物**：将工具和依赖构建为固定版本的工具镜像，记录来源、依赖、构建日志及镜像摘要。相同请求以后复用缓存。
5. **验证可用性**：检查命令、导入、启动及最小功能。验证通过后才能标记为可用，不能只以安装退出码或命令存在作为依据。
6. **离线执行**：控制器使用工具镜像启动无网络、非 root 的执行容器，只提供指定输入和受控输出目录。结果、产物和日志进入现有证据体系，agent 获得结果后继续解题。

构建容器与解题容器之间只交付固定的工具产物，不共享题目数据、敏感挂载或运行状态。允许访问的软件仓库仍存在供应链风险，因此来源限制、版本固定和构建隔离需要同时成立。

## 基础镜像与扩展环境

保留覆盖常见需求的基础镜像，低频或较大的工具按需供应。

| 需求 | 使用方式 |
|---|---|
| 常见命令和 Python 库 | 基础沙箱直接执行 |
| 缺少 Python 库，且脚本需组合多个库 | 基于基础镜像生成扩展环境，在其中执行完整脚本 |
| Ghidra、Sage、OCR 等较大工具链 | 使用缓存的专用工具环境 |
| 需要设备、额外权限或外部服务 | 报告明确条件，再决定是否授权 |

例如，pytesseract 需要调用 tesseract 程序，cv2 又有自身的 Python 和原生依赖。应把这组依赖作为同一个环境验证，不能分别安装成功后就假设组合脚本可运行。

专用环境既可以提供单项工具调用，也可以执行完整解题脚本。后者适合多个库需要在同一进程中协作的情况。

## 与当前解题机制衔接

建议新增以下控制器接口；接口名称和字段属于设计建议：

- `tool_request`：申请能力或依赖，返回缓存命中结果、准备任务 ID 或无法满足的原因。
- `tool_status`：查询准备进度、验证结果和工具环境标识。
- `tool_exec`：在指定的已验证环境中执行命令或脚本，提供受控输入，保存输出与执行证据。

工具环境注册到当前运行的能力清单中。Agent 得知新能力后重新检查前置条件，再继续原来的尝试。已有工具不可用时应返回结构化的缺失原因，而不是要求 agent 在普通解题命令中安装软件。

工具准备不应改变解题成功的判据，也不应自动扩大题目网络授权。工具安装成功只表示获得了执行能力，不表示某个解题假设已经成立。

## 关键边界

### 解题连续性

保留主沙箱及正在运行的交互会话，避免为了增加工具直接重启整个沙箱。当前 `/work` 若使用 tmpfs，应由控制器导出指定输入，并把新产物导回证据与工作区；不能假设多个容器天然共享主沙箱的临时文件。

确需共享目录时，由控制器管理路径、读写范围和生命周期，不把宿主工作目录整体挂载进去。原始附件保持只读。

### 来源与执行权限

常规请求使用允许的软件仓库和固定的构建模板。任意 URL、私有源、额外设备和权限不应通过包名或安装脚本间接获得，需要单独处理。

构建环境限制可访问的网络目标，并避免携带解题环境中的敏感信息。安装依赖可能执行构建脚本，因此不能把安装视作单纯下载文件。

### 资源与失败处理

限制构建时间、磁盘、内存和并发；支持取消及清理临时资源。失败时区分软件下载失败、依赖冲突、版本不兼容、验证失败和权限不足，避免 agent 反复提交相同请求。

失败的准备任务不能污染已验证缓存，也不能替换当前可用环境。取消后不得把未完成验证的产物标记为可用。

### 缓存与可追溯性

缓存键应包含基础镜像摘要、系统架构、软件源、依赖版本及构建配置。执行时引用固定镜像摘要，避免同名标签变化后环境悄然改变。

每次工具调用记录所用环境、输入、命令、退出状态、日志和输出文件引用。高频扩展可以定期合入基础镜像，低频工具继续按需供应。

### 工具能力限制

GUI 工具安装成功不等于 agent 能操作其界面；应优先提供命令行或 headless 入口。虚拟显示可用于启动部分 GUI 程序，但不会自动提供交互能力。

设备访问、Android 动态分析、在线服务、特定版本编译器及许可证要求，需要分别说明其运行条件。无法满足时明确报告，不把工具标记为完整可用。

## 用户交互

沿用现有 TUI 风格展示工具供应状态：检查缓存、准备依赖、验证工具、已可使用或失败。失败信息应说明具体阻塞条件及保留的解题状态。

常规、符合策略的工具供应自动完成，用户无需参与每次安装。只有超出既有授权的来源、权限、设备或服务需求，才单独请求决定。

## 预期收益与限制

该机制可减少缺工具导致的中断，省去大多数人工改镜像操作，并将安装网络与解题网络分离。缓存可以降低重复构建成本，固定环境和证据记录有助于复现。

它不能保证所有工具都可自动获得或在现有隔离条件下运行。首次准备仍需要时间，复杂依赖可能冲突，设备、许可证和外部服务条件也不能仅靠安装解决。
