# 从最小闭环逐步扩大到最终目标的路线调整设计

日期：2026-09-30  
状态：已通过对话设计评审；等待书面稿评审。

## 1. 目的

调整 ctfbot 的开发路线，使项目先交付范围清楚、端到端可用的闭环，再逐轮扩大支持的题目、运行模式和产品能力，直到达到现有设计定义的完整目标。阶段完成表示该阶段约定范围内的闭环可用，不表示系统已经完美；最终完成才表示原定产品目标均有可追溯的验收结果。

## 2. 当前基线与计划问题

阶段 A 记录将 headless agent loop、离线 synthetic baseline、evidence、controller verifier、工具注册表、Codex adapter、Docker runtime adapter 和 batch runner 记为最小闭环的一部分。一次经明确授权的 cry-babycrypto smoke 得到 `verified`；10 道私有本地 pilot 已准入，但正式数据仍标记为未授权发送给模型。批量真实 baseline 未运行。

阶段 A 的部分扩展验收仍未完成，包括 Docker 的更广异常/宿主隔离负面检查、provider usage/error/cancel 语义和批量评测。阶段 A 记录已明确它们不阻塞最小闭环，但详细计划仍将若干宽泛验收设为阶段门槛。当前阶段 B 又把正式 TUI、运行生命周期、多个领域包、报告、评测命令等同时列为一个 MVP 交付，容易把“完成第一条产品闭环”推迟到大量配套能力全部完成之后。

## 3. 已确认的设计原则

1. **闭环优先。** 每一轮都交付从题目输入到明确结束状态的可运行路径。最初支持范围可以窄，之后按实际需要扩大。
2. **安全性质是每轮底线。** 授权范围、sandbox/网络隔离、资源预算、controller-only oracle、verified 状态准确性和 evidence 可追溯性不能因为“先完成”而延期。
3. **区分最低门槛与扩展验收。** 每个里程碑标出必须通过的范围内检查、阻断问题，以及范围外的扩展项和重新评估触发条件。
4. **真实模型使用按题目和预算授权。** fake/synthetic 路径用于可重复工程验证；真实题目传输和模型预算按单独授权执行，不将一次性授权推广到其他题目。
5. **高级架构由证据决定。** 多 agent、题解 RAG、race 和并行 worker 需要同预算对照显示有净收益，才进入默认产品路线。
6. **不以完美作为里程碑门槛。** 范围外的兼容性、广泛异常覆盖和界面打磨进入有风险、触发条件和复查节点的 backlog；未解决的高风险安全或结果可信度问题仍阻断对应能力发布。

## 4. 逐层扩大的路线

### 阶段 A：已完成的工程基线

保留现有 headless 最小闭环及其实际验收记录作为基线。阶段 A 不因扩展验收尚未完成而重新打开，也不将该基线表述为完整产品或广泛安全认证。

### 阶段 B：第一条可用的产品闭环

交付一条范围受限但从头到尾可用的路径：导入/预览获准的本地附件题，通过 TUI 启动并观察单 agent 运行，使用首批 core 工具，提交候选并由 controller verifier 判定，查看 evidence 并导出基础报告。TUI 先实现完成这条路径所需的功能。

该阶段不要求一次覆盖六大类、交互式 session、远端目标、高级布局或大规模 benchmark。对不支持的运行模式必须明确拒绝。真实模型试题仅在对应题目重新获得传输与预算授权后执行；fake/synthetic 路径可先完成集成验证。

### 阶段 C：按能力逐轮扩大运行闭环

按依赖和风险依次加入可靠运行生命周期、交互式 session、本地服务题和显式 allowlist 远端题。每种新模式单独定义输入/授权、网络和文件边界、资源预算、错误/取消/清理语义及其验收题。

扩大到某种不可信执行或联网模式前，完成直接约束该模式的隔离负面检查。provider usage、错误和取消语义在依赖其管理长任务、成本或批次前完成。每个增量都保留已交付的端到端路径。

### 阶段 D：领域覆盖、泛化评估和最终闭环

按现有领域设计逐步交付工具包，直到约定的六大类均有代表性基础工作流和验证样例；开始领域扩展时，先将现有工具包分组映射为明确的六类覆盖矩阵，混合/未知题型作为跨类回退能力记录，不替代类别覆盖。建立受控的公开、改编及私有评测集，报告 verified/candidate/unsolved/environment-error 的分子和分母、成本、人工介入、复现情况及数据污染说明。加入通用记忆前，验证来源、许可、答案污染和盲测隔离流程。

最终验收覆盖：TUI 与 headless 共用 application service；支持模式有端到端闭环；候选与 verified 状态可信；evidence、报告和复现材料可追溯；六大类覆盖矩阵完整；评测与记忆治理符合上述要求。项目不承诺所有题目可解，也不凭空设定 solve-rate 门槛；评测结果必须如实呈现。

## 5. 统一的里程碑门槛

每个增量均记录：

- **闭环范围**：支持的输入、运行模式、题型、provider 和明确不支持的路径。
- **进入条件**：上一闭环的回归路径通过；本轮题目授权、数据范围和模型/运行预算清楚。
- **完成条件**：代表性输入能从导入走到明确结束状态；工具结果有 evidence 引用；候选与 verified 状态准确；报告或结果视图不虚构未记录的动作；本轮启用模式的安全边界和失败清理检查通过。
- **阻断问题**：越权访问、未授权网络或数据传输、secret/oracle 暴露、预算不能强制执行、未验证却标为 verified。任何一项都阻断对应能力。
- **后续完善项**：注明延后风险、触发条件、目标验收、复查节点和责任阶段。范围外项目不得被当作当前里程碑的隐含阻塞项。

## 6. 阶段 A 未完工作的重新排期

| 未完工作 | 重新排期原则 |
|---|---|
| Docker 更广异常路径与宿主隔离负面检查 | 在接入相应不可信镜像、mount 或运行模式之前完成；当前 synthetic smoke 不描述为完整安全认证。 |
| Provider usage/error/cancel 语义 | 在依赖精确 usage、provider 重试、长任务控制或批量成本统计之前完成。 |
| 批量真实 CTF baseline | 第一条产品闭环可用后，针对明确获准的题目和预算分批运行；不把既有单题授权扩展为批量授权。 |
| TUI 正式工作台 | 阶段 B 实现满足第一条产品闭环的最小界面，后续按实际使用反馈扩展。 |

## 8. 范围外事项

此路线调整本身不实现 TUI、runtime、工具包、memory 或 benchmark 功能；不新增多 agent、题解 RAG、Web UI、平台账号接入或云端 worker 目标；不承诺 benchmark 成绩或特定成功率。上述能力须按路线里程碑另行实现和验收。
