# 多子题 Flag 逐步提交与实时查看修改计划

日期：2026-10-09
状态：已实施，确定性验收通过。实际修改与测试结果见 [multi-flag-progress-implementation.md](multi-flag-progress-implementation.md)；以下保留原计划设计。

## 1. 目标

一题包含多个子题或阶段性 Flag 时，Agent 每发现一个有证据支持的 Flag，就立即通过 `candidate_submit` 记录并向用户展示，然后继续求解其他部分。用户无需等待整个运行结束，即可查看、选择和复制已得到的 Flag。

目标流程：

```text
解出第一子题 → 提交 Flag A → 用户可查看、复制 A
                  ↓
继续第二子题 → 提交 Flag B → 用户可查看、复制 A、B
                  ↓
全部完成或无合理后续步骤 → 显式结束并汇总已获得结果与未解决项
```

“提交候选”“用户查看候选”“结束本次运行”是独立操作。提交和查看均不停止模型、不关闭沙箱、不要求用户确认后才能继续求解。

## 2. 当前实现与原因

| 位置 | 当前行为 | 需要改进的地方 |
| --- | --- | --- |
| `agent/loop.py` 初始提示词 | 要求判断为 Flag 时提交，但没有明确多子题逐个及时提交的规则 | 明确提交时机、提交后继续及整体结束条件 |
| `tools/reliability.py` 的 `candidate_submit` | 可多次记录候选，返回 `ends_run=False` | 加入可选子题标签，工具描述强调即时交付 |
| `tools/reliability.py` 的 `run_complete` | 明确结束运行，仅有单个 `candidate_id` 字段 | 允许一次结束关联多个已提交结果，兼容单候选用法 |
| `tui/app.py` | 已接收运行中提交事件，但 Flag 按钮与打开逻辑要求运行结束 | 改为运行中可访问，按当前运行隔离数据 |
| `tui/candidates.py` | 候选窗口使用打开时传入的固定候选列表 | 支持增量更新，保留用户当前查看位置 |

没有具体运行日志时，不能仅凭“用户尚未看到 Flag”断定模型尚未提交；实施和复盘应区分模型延后调用工具与界面限制查看两种情况。

## 3. 行为设计

### 3.1 发现一个就提交一个

同时修改初始提示词、续轮提示词和工具描述，保持一致：

- 对包含多个问题、多个阶段或多个 Flag 的题目，每得到一个有证据支持的候选，先调用 `candidate_submit`，再开展后续子题实验；不等全部子题完成后集中提交。
- 提交时保留 Flag 原始字符和前缀，可附带子题标签、来源观察、推导说明、检查结果；尚未检查时填写原因，不因等待完整验证而隐瞒已得到的候选。
- 提交后继续尚未解决的部分；第一条 Flag 不是整体完成的依据。子题范围依据题目与用户要求判断，不凭空推断还存在其他 Flag。
- 不要求先更新摘要才能提交 Flag。提交后在合适的公开进度更新中说明“已得到哪些结果、正在做什么、剩余哪些部分”。
- 全部已知要求完成，或没有合理后续步骤时，才调用 `run_complete`。尚有未解部分时如实列入 `unresolved`，不得宣称全部解决。

仅修改提示词不能保证真实模型始终及时提交。控制器不从普通工具输出中用正则自动提取 Flag，也不根据疑似 Flag 强制中断；通过测试与运行日志观察模型实际提交时机。

### 3.2 候选增加子题标签

`candidate_submit` 增加可选字段 `subtask`，用于简短的人类可读标签，例如“第一问：恢复密钥”“第二阶段”。建议上限 160 字符，省略时显示“未标注子题”。

- 字段进入候选记录、证据详情、工具返回、`state_read` 与上下文恢复中相关候选信息。
- 不要求模型提前登记完整子题清单，不引入子题数量、完成率等未经证实的数据。
- 保留现有 `candidate_id` 和原文证据存储方式。标签是模型提供的说明，不改变候选验证状态。
- 同一子题可有多个候选；同一原文也可能对应不同子题，不按原文全局去重。UI 按当前运行内的 `candidate_id` 避免同一事件重复展示。
- 原有调用与旧日志无需新增字段即可使用。

### 3.3 多候选结束汇总

`run_complete` 增加可选 `candidate_ids` 列表，关联本次结束保留的多个候选；旧 `candidate_id` 继续可用。

- 统一归一化为去重且保序的候选 ID 列表。两个字段同时出现时取并集，所有 ID 都必须属于当前运行。
- `outcome='candidate_unverified'` 至少关联一个候选；`unsolved` 沿用原有语义。存在部分成果时优先使用 `candidate_unverified`，并在 `unresolved` 描述未解部分。
- 完成记录、工具返回和报告保留完整列表；旧单候选字段保留既有含义，不能因新增列表遗漏旧消费者需要的字段。实施时检查所有完成记录消费者。
- 用户可继续查看全部曾提交的候选，即使某个候选未被最终汇总选中。不要把早期候选从历史中删除。
- 不引入平台正确性判定，也不因某个局部检查通过而将候选改为“已验证”。

## 4. TUI 交互设计

### 4.1 运行中入口与通知

- 运行中允许打开 Flag 窗口，无候选时展示“尚未提交 Flag，解题继续中”。按钮显示已提交数量，例如 `Flag · 2`。
- 收到成功的 `candidate_submit` 结果后立即更新数量，并给出简短提示“已记录：第一问 · candidate-1，继续解题中”。不自动弹窗、不抢输入焦点，也不强制滚动运行记录。
- 不显示无法确认的“已解出 N/M”；数量只表示候选记录数，不等同于已解决子题数。

### 4.2 候选窗口动态更新

- 在现有窗口基础上展示候选 ID、子题标签、候选状态及只读原文，复用已有复制按钮和选区复制。
- 窗口打开期间新增候选时更新选择列表和数量；保留当前候选、文本选区、滚动位置及复制操作状态，不自动切到最新候选。
- 首条候选到达空窗口时自动填充第一条；之后通过选择列表主动切换。新增提示可显示“新增 1 条候选”。
- 关闭窗口仅返回运行视图，模型继续执行。运行自然结束或用户停止时，窗口继续保留本次已有候选，更新运行状态。
- 复制始终读取用户所选候选的原始内容；后台新增记录不能改变正在复制的值。标签及状态不混入复制内容。

### 4.3 数据与事件处理

- 由 App 在 UI 线程维护当前运行的候选集合，使用现有事件消息增量更新；候选窗口只是该集合的视图，不自行轮询日志。
- 成功提交并落盘的事件是展示依据，不能从模型普通文字或工具调用参数提前认定提交成功。证据读取复用既有 hash 校验、大小限制和控制字符转义。
- 当前运行 ID 与证据目录从运行初始化事件取得，运行中不依赖尚不存在的 `last_result`。开始新运行时清空旧集合；忽略其他运行的迟到事件。
- 运行结束后或查看历史结果时，仍可从日志重建候选。旧记录缺少 `subtask` 时正常回退显示。
- 检查弹窗位于屏幕栈顶时，App 的运行消息处理和控件查询是否仍能正确访问主运行视图；必要时明确使用主屏幕引用，避免弹窗打开后进度更新异常。
- 不改变历史记录的手动跟踪策略、剪贴板跨平台策略或累计额度已取消的行为。

## 6. 验收标准

1. 合成 provider 按“提交 A → 执行第二子题工具 → 提交 B → 完成”运行；确认 A 提交后运行未结束、第二子题工具实际执行，最终保留两条记录。
2. 运行保持活动且最终结果尚不存在时，打开 Flag 窗口即可查看并复制 A；窗口保持打开时 B 到达，列表立即更新，正在查看的 A、选区和复制内容保持稳定。
3. 空窗口打开后第一条候选到达、后台新增多条、窗口关闭重开、运行结束和用户停止等路径均可正常展示已有结果。
4. 新运行不会混入旧运行候选；重复投递同一候选事件不会重复计数；提交失败不增加候选数。
5. `subtask` 缺省、中文、长标签及控制字符安全展示；复制保持原文，多行及特殊字符不被标签或显示转义污染。
6. 单 `candidate_id` 旧调用、多 `candidate_ids` 新调用、同时指定两字段、空列表、未知 ID、跨运行 ID 均按约定处理；旧日志与新报告都可读取。
7. 验证提示词和工具描述包含“每个子题及时提交、提交后继续、剩余项如实说明”，且不再暗示先完成摘要或全部求解后才提交。
8. 运行消息在弹窗打开时仍正常更新；关闭弹窗后运行记录、statusline 和手动历史跟踪行为正常。

优先扩展 `tests/test_unknown_flag.py`、`tests/test_agent_reliability.py`、`tests/test_context_management.py`、`tests/test_tui_candidates.py`、`tests/test_stage_b_tui.py` 和相关报告测试。UI 测试使用受控事件与同步点模拟持续运行，不依赖真实模型或桌面剪贴板。

可选真实模型验证使用自制的两子题样例，观察第一次得到 Flag 到 `candidate_submit` 之间的调用顺序；若模型仍延后提交，再依据日志调整指引。模拟 provider 的成功只能证明执行与展示链路支持该流程，不能证明真实模型必然遵守时机要求。

## 7. 完成边界

本计划不实现比赛平台自动提交、不增加正确性 oracle、不从任意输出自动猜测 Flag、不扩展为跨运行续解，也不为第一条 Flag 设置自动停止规则。本次交付重点是多结果及时交付、后续求解持续进行，以及运行中随时查看复制。
